# Design system

Firefly's interface is built on one small design system, written for this project. It is informed by Microsoft's public Fluent 2 web themes (the light theme's colour values and the type ramp were checked against Microsoft's open-source Fluent UI tokens) but it is an original implementation: Fluent UI React is not used, no Microsoft asset is copied, and the logo mark is Firefly's own. The interface has **two themes**, light and dark. The dark theme is authored on its own, not inverted from the light one, and the page follows the device's setting until the person chooses one (see [Themes](#themes)). It uses the system's Segoe UI Variable where it exists, and system fonts elsewhere; no web font is downloaded.

## Direction (the brief for every screen)

| Question         | Answer                                                                                                                                                                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Purpose          | A new Microsoft support engineer practises a customer call by voice and learns from coaching grounded in the transcript.                                                                                                                                                               |
| Audience         | Apprentices and new hires, on a corporate Windows laptop, repeating the same flow: scan, choose, speak, review. They need status at a glance and almost no reading.                                                                                                                    |
| Tone             | Microsoft 365 and Dynamics: calm, compact but breathable, one blue for actions and selection, neutral everything else, subtle elevation, clear commands and clear status. Icons with concise labels.                                                                                   |
| Memorable detail | The product shows itself: the landing page's hero is a short scripted call that plays beside the promise (no audio, no microphone) and turns into a small report, drawn with the design system's own badge, avatar and score components, and every movement exists to explain a state. |
| Constraints      | Fluent 2 principles, system fonts, a strict CSP (same-origin scripts and styles only: no inline script, no inline style in markup), bundle budgets (`scripts/budgets.json`), WCAG 2.2 AA, a light and a dark theme, no dependency added.                                               |
| Target viewports | 320, 375, 430, 768, 1024, 1280, 1440 and 1920 px wide; text at 200 per cent; reduced motion; forced colours; both themes; the report on paper.                                                                                                                                         |
| Never            | Glass, neon, decorative gradients, 3D, particles, a cosmic metaphor, gamification, paragraphs that explain what a control already says, card grids as a layout habit.                                                                                                                  |

The one place the "never" list is brushed: under a mouse, an interactive card rises a little, turns by no more than 2 degrees (1.5 by default) and catches a soft light that follows the pointer (see [Interaction](#interaction)). That is feedback for a fine pointer only, never on a touch screen, and none of it moves under reduced motion.

Slop check (generic AI-made design patterns): no gratuitous gradients (the only gradients are the sweep of a shimmer and the stripes that replace it under reduced motion); no purple-to-blue defaults (the indigo `--ai-*` accent marks the provider and nothing else); **glass removed** (the sticky header was 78 per cent white with a 20 px backdrop blur: now a solid surface with a hairline, which also costs nothing to paint); radii follow one scale (4 controls, 8 panels, 12 dialogs); no motion on scroll; the hero is left-aligned beside a real preview, not centred text over a gradient; the font is the system's, deliberately.

## Principles

- **Calm and legible.** A quiet canvas (white in the light theme, charcoal-navy in the dark one), restrained neutrals, one brand blue for actions, selection and active state. Nothing decorative moves on its own: a lift, a tilt or a small waveform answers a mouse or the keyboard.
- **Little text.** A label, an icon or the layout says it first; detail is folded behind a disclosure. Landing and content pages have copy budgets that tests count from the rendered DOM.
- **Colour never carries meaning alone.** Customer mood, scores, status and found/missed facts always have a word, and mood has a distinct icon shape for each of its six states.
- **Native first.** Native `<dialog>`, `<select>`, radio groups and checkboxes where they do the job, with roving tabindex only where a pattern needs it (tabs).
- **Targets are large.** Primary controls are 44 px high, dense controls 32 px, and nothing is below 24 px.
- **Motion explains, then stops.** Short, interruptible transitions; only `transform` and `opacity` move; every movement has a still equivalent under `prefers-reduced-motion`; nothing repeats for more than a few seconds unless it is the state itself or the person can stop it (the landing page's call preview, which also rests after three loops).
- **Two themes, one set of names.** Components read semantic tokens only, so a theme is a set of values and no component knows which one is on, with one exception: the call and pre-flight screens choose which surface they sit on for each theme (see Themes). The dark theme is authored for dark surfaces, not inverted from the light one.
- **Text is plain.** Anything from a user or a model is rendered as text, never as HTML.

**Product accents.** Each of the 13 products has one of seven hues (`PRODUCT_ACCENT` in `web/src/design/product-accent.ts`), so a scenario is recognised at a glance. `accentClass(product)` returns `ff-accent ff-accent--<hue>` (blue for a call saved with no product), and `web/src/design/accent.css` turns that class into three local properties, `--accent-fg`, `--accent-bg` and `--accent-border`, resolved from the active theme's tokens. A component reads those and never names a hue, so a product can change hue in one place. An accent is a small mark (an icon tile, a thin edge, a tag), never a large fill, and never the only way a product is named: its name is always written. The hues are plain picks from the palette, not product logos. A test checks that every product has a hue and that at least six of the seven are in use, and `tokens.test.ts` checks each hue's text on its tint and on the page in both themes.

Breakpoints cannot be custom properties, so they are written as media queries: 30em (480), 40em (640), 48em (768), 64em (1024), 80em (1280), 90em (1440) and 120em (1920).

## Themes

The interface has a light and a dark theme. The light theme is the `:root` block of `web/src/design/tokens.css`. The dark theme is a second block in the same file, `:root[data-theme='dark']`, written inside `@media screen`. Components use semantic tokens only, so a theme is a set of values and no component knows which one is on, with one exception described below.

**The dark theme is authored, not inverted.** It is a charcoal-navy canvas whose surfaces get lighter as they come nearer (`--bg-canvas`, `--bg-quiet`, `--bg-subtle`, `--bg-section`, `--bg-strong`), with strong text, quiet borders and shadows made of black only, with no coloured glow. The blue stays a Microsoft-style blue for actions, a cyan (`--voice-customer`) is kept for the live customer voice, a customer's concern is amber, and a call that escalates moves from orange to red. No surface is pure black or pure white. Every colour and depth token the light theme declares is declared again in the dark block, and the dark block declares nothing the light one does not. The one place a stylesheet picks surfaces by theme is the call and its pre-flight page. In the light theme the page is a grey (`--bg-subtle`) with white cards (`--bg-canvas`) on it. In the dark theme a surface gets lighter as it comes nearer, so the page is the darkest (`--bg-canvas`) and the bar, the dock and the cards are a step up (`--bg-raised`; the call's panels from 64em, and below that they are the page itself). That is written in `:root[data-theme='dark']` rules of `workspace.css`, `preflight.css` and `call-states.css` in `web/src/features/call-ui/`. The table shows the main differences; the rest is in `tokens.css`.

**The brand blue has three jobs.** In the light theme one blue does all of them. In the dark theme it cannot. A fill that carries white text has to be dark enough (`--brand`, 5.28:1 with white), but that blue is only 3.30:1 as a line or as text on the dark canvas, and the lighter blue that works there (`--brand-fg`, 7.19:1 on the canvas) is only 2.42:1 under white text. So the tokens are split by job:

- `--brand`, `--brand-hover`, `--brand-pressed` and `--brand-selected` are solid fills that carry text, such as a primary button.
- `--brand-stroke` (and the softer `--brand-stroke-2`) is for lines, bars and indicators: the tab and header indicators, progress bars, the border of a focused field.
- `--brand-fg`, `--brand-fg-2` and `--brand-fg-hover` are for text and icons. Links use `--brand-fg-2`, and a link under the pointer uses `--brand-fg-hover` (`a:hover` in `base.css`, and the report's "Show more" button). `--brand-pressed` is not used for that: it is a fill, and it stays dark in both themes.

In the light theme `--brand`, `--brand-stroke` and `--brand-fg` are the same `#0f6cbd`, and a test says so, so nothing moved there.

**Choosing a theme.** The person can choose Light, Dark or System. System, the default, follows the device.

- `ThemeToggle` is in the header. It is a 44 px square button whose name is always "Dark theme" and whose pressed state (`aria-pressed`) says whether dark is on. The sun turns into a moon: a mask slides over the disc while the rays turn and fade, by transform and opacity only, and under reduced motion it is a plain swap. In the public header it is in the bar at every width. In the app header it is in the bar from 48em, and below that on a row labelled "Theme" inside the header's menu.
- `ThemeSelect` is in the footer: Light, Dark and System as one native radio group, so the arrow keys move and choose. "Saved on this device" hangs above it for 2.4 seconds after a choice the browser kept, and a screen reader is told once ("Light theme saved on this device.", "Dark theme saved on this device." or "System theme saved on this device.") through the page's single polite announcer. When the browser blocks storage the choice still applies for the visit but is not kept, and the control says so instead: "Not saved: storage is blocked", and the announcer says "Dark theme applied. This browser is not keeping it." (`storePreference` returns whether the choice was kept; `web/src/design/theme/ThemeProvider.test.tsx` covers the blocked case).
- `ThemeProvider` wraps the app, first in `AppProviders` (`web/src/App.tsx`). It reads the saved choice, follows the device's `prefers-color-scheme` while the choice is System, follows a choice made in another tab (the `storage` event), and puts the result on `<html>`: `data-theme` (`light` or `dark`), `data-theme-preference` (`light`, `dark` or `system`) and the colour of the `theme-color` meta tag (`#ffffff` or `#161a22`). It does not set `color-scheme`: the stylesheet does (see Print, below). Both controls render nothing outside a provider, so the four development galleries, which mount none, have no switch and follow the saved or the system theme.

**Where the choice is kept.** In `localStorage`, under the key `firefly.theme`, as `light` or `dark`. System is stored as no key at all, and anything else found in the key is read as System. The choice is never sent to the server. If storage is blocked the theme still works for the visit; it is just not remembered, and the footer choice says so (see above).

**Before the first paint.** `web/public/theme-init.js` is a short classic script that `web/index.html` loads from `<head>`, before the app. It reads the saved choice and the device's `prefers-color-scheme` and sets the two `data-theme` attributes and the `theme-color` colour, as the provider does, so a person who chose dark, or whose device is dark, never sees a flash of the light page. Like the provider, it never sets `color-scheme` (see Print, below). It is a file and not an inline snippet because the page's content security policy allows scripts from its own origin only (`script-src 'self'`, in `server/http/security.ts`), so an inline script would be blocked. If storage is blocked the device's setting decides, and if the browser cannot answer media queries the page is light. The script mirrors `web/src/design/theme/theme.ts`, and a test runs the file against the same inputs as the app's own code. `index.html` also declares `<meta name="color-scheme" content="light dark">`.

**The crossfade.** When the person changes the theme, `withThemeTransition` (in `theme.ts`) uses the browser's View Transitions API to crossfade the whole page, and `theme.css` sets the root's old and new views to `--motion-page` (400 ms) with `--ease-easy`. Where the browser has no View Transitions, or the person asks for reduced motion, the page changes at once. Only a change the person makes is animated: the first paint, a change of the device's setting and a choice made in another tab are not.

**Print, forced colours and more contrast** are separate paths. The dark block applies on screen only, so a printed page is always the light document, and the theme controls, the headers and the footer are hidden on paper. `color-scheme` follows the same rule: `tokens.css` sets `light` in `:root` and `dark` inside that screen-only block, and no script sets it inline. An inline value would also reach print, where the printed report is drawn in the system colours `Canvas` and `CanvasText` (the `@media print` block of `report.css`), so a report printed from the dark theme would come out as white text. In forced-colours mode components use system colours, and the theme switch's sun and moon are drawn in `CanvasText`. `prefers-contrast: more` has a block for each theme in `tokens.css`, which strengthens `--stroke-1` to `--stroke-3` and `--fg-3`.

**What polices it.**

- `web/src/design/tokens.test.ts` reads `tokens.css` as text. In both themes it checks the text and graphic pairs (see [Contrast and accessibility](#contrast-and-accessibility)). It also checks that the dark block sits inside `@media screen`; that every colour and depth token exists in both themes, and the dark block adds none of its own; that the dark surfaces form a ladder up from the canvas, none of them pure black or white, with `--fg-1` at least 12:1 on the canvas; that the voice cyan leans cyan and the concerned and frustrated states lean warm; that in the dark theme the brand fill is darker than the stroke and text blues; and that the dark shadows are black only.
- `web/src/design/theme/theme.test.ts` covers the pure code (reading, storing and resolving a choice, whether it was kept, applying it to the page without setting `color-scheme` inline, the crossfade). `theme-init.test.ts` runs `theme-init.js` itself, which must leave `color-scheme` alone, and checks that `index.html` loads it from the head before the app, has no inline script and declares both colour schemes. `ThemeProvider.test.tsx` covers the provider, the toggle and the footer choice: the system's theme, a saved choice, another tab, the keyboard, the words, blocked storage, and no provider.

## Motion

One rule set, enforced by `design/motion.test.ts` and `design/tokens.test.ts`. `motion.test.ts` reads every stylesheet under `web/src` (the design system, the shell and every feature) as text, and `tokens.test.ts` reads the tokens:

1. **Only `transform` and `opacity` move.** A transition may also change colour, border colour or shadow for hover, press and selection (paint only); never a layout property, never `all`. A keyframe moves `transform` and `opacity` only. (Why: a width, inset or margin that animates moves the page under the person's hands.)
2. **Every time comes from a token.** No stylesheet writes `200ms`. Each `--dur-*`, `--move-*` and `--press-*` token has a still equivalent in the reduced-motion block of `tokens.css` (durations 0.01 ms, distances and `--press-grow` 0), and a test fails if one is added without it. `base.css` ends every animation and transition under `prefers-reduced-motion: reduce` as a floor.
3. **Movement explains state.** The press compresses a button 1 px (2 px for the large one); a main action's arrow leans on hover and focus; a new row or panel rises a few pixels as it fades in (`u-enter`, `u-fade`); a status word fades in place; a score fills once, from empty, when motion is allowed; tab panels crossfade in one cell, so nothing below them moves; a sliding indicator moves under the current link; the theme switch's sun turns into a moon, and the page crossfades when the theme changes; under a mouse an interactive card rises `--move-lift` (2 px), turns a degree or so, catches a soft light and shrinks by `--press-grow` (1.5 per cent) while it is pressed.
4. **Nothing repeats for long.** The landing page's call preview is a loop of 15 seconds that plays three times and then rests on its final frame, a small report. A "Pause preview" button stops it (WCAG 2.2.2) and then reads "Play preview"; after the third loop it reads "Replay preview" and plays the whole call again, with focus staying on the button. It also pauses by itself while it is off screen or the tab is hidden, and under reduced motion it shows the final frame with no button, because nothing moves. The only endless motion is the state itself (a spinner, a progress shimmer, a listening pulse), still under reduced motion.
5. **The spring is for four places.** `--dur-spring` and `--ease-spring` are used only for a dragged carousel item settling, a tip card released after a drag, a call control being pressed, and the report's evidence panel and better wording coming into view. Dialogs, pages, the theme change, a transcript turn arriving and a report section opening use plain easing. `motion.test.ts` keeps the list of stylesheets that may name `--ease-spring` (`design/carousel/`, `features/tips/`, `features/call-ui/controls.css` and `features/report/`). The easing is a `cubic-bezier` that overshoots a little; a browser that understands `linear()` is given a spring-shaped curve instead.

### The five tiers

The interaction system names its durations by what they are for. A tier is a name for a duration token, so reduced motion collapses it with the rest.

| Tier                 | Duration | Names          | What uses it today                                                                                                                                    |
| -------------------- | -------- | -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `--motion-instant`   | 100 ms   | `--dur-faster` | A press or a toggle: the theme switch, the product rail.                                                                                              |
| `--motion-control`   | 150 ms   | `--dur-fast`   | Hover and focus on a small control or a card: the carousel's arrows, the tip cards, the header indicator fading.                                      |
| `--motion-component` | 200 ms   | `--dur-normal` | A component changing state: the sliding indicators, the carousel's items, the sun and the moon.                                                       |
| `--motion-panel`     | 300 ms   | `--dur-slow`   | A panel: the tips sliding along their track, the call preview turning into a report, the three steps lighting, the product tile carried to the brief. |
| `--motion-page`      | 400 ms   | `--dur-slower` | A page. Today only the crossfade when the theme changes.                                                                                              |

`--dur-stagger` (40 ms) is the step between items that arrive one after another.

### Under reduced motion

| What                            | What the person gets                                                                                                    |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Tokens                          | Every `--dur-*` is 0.01 ms; `--move-*`, `--press-shift*` and `--move-lift` are 0; `--press-grow` is 0.                  |
| Everything else                 | `base.css` ends every animation and transition (0.01 ms, one iteration, no delay) and sets `scroll-behavior` to `auto`. |
| Mouse effects                   | No tilt, no pointer light and no drag stretch (`pointerFxEnabled` is false). A mouse can still drag.                    |
| Carousel                        | The window jumps to an item instead of gliding, and there is no spring settle.                                          |
| Theme change                    | No View Transition: the page changes at once.                                                                           |
| Landing call preview            | The final frame, whole, with no Pause, Play or Replay button, because nothing moves.                                    |
| Status strip on the call screen | A still level meter instead of moving bars; the three points of a customer working out a reply stay still.              |
| Tips                            | A tip changes at once: no glide, no lift, no tilt.                                                                      |

## Interaction

The hooks behind mouse, scroll and in-view behaviour are in `web/src/design/interaction/` and are exported from the design barrel. The mouse hooks write custom properties and data attributes for a stylesheet to use, and change no React state on a pointer move.

| Export                             | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `pointerFxEnabled`, `usePointerFx` | The one place that decides whether mouse effects are allowed. They are on only when the main input can hover and is fine (`(hover: hover)` and `(pointer: fine)`) and none of `(prefers-reduced-motion: reduce)`, `(prefers-reduced-data: reduce)` and `(update: slow)` matches. Browsers have no API for low-power mode, so these queries are proxies, and the code claims no more than they say.                                                                                                                                                                                                                                                                                               |
| `useTilt`, `tiltFor`               | Turns an element toward the mouse by at most 1.5 degrees (a larger maximum is held to 2) and writes `--tilt-x`, `--tilt-y`, `--glow-x` and `--glow-y`, plus `data-fx="on"` or `"off"`. One write per animation frame; touch and pen are ignored; the properties are removed when the mouse leaves. Nothing is listened to where effects are off.                                                                                                                                                                                                                                                                                                                                                 |
| `useDragScroll`, `decideSwipe`     | Mouse drag-to-scroll for a row that scrolls sideways. Only a mouse with its main button drags; touch and pen keep the browser's scrolling. A press that moves under 6 px stays a click, and the click that ends a drag is swallowed, so a drag never selects. While it drags, the element carries `data-dragging="true"` and snapping, smooth scrolling and text selection are off. At either end the drag stretches (`--drag-overscroll`: a third of the movement, at most 48 px) where effects are allowed. `decideSwipe` turns a release into next, previous or none from distance and speed: 48 px, or a flick of at least a third of that at 0.35 px per ms. Speed never replaces distance. |
| `useInViewOnce`, `useOnScreen`     | Wrappers for `IntersectionObserver`. `useInViewOnce` is true once the element has been seen, and then for good: the landing page's steps and report preview use it to light as they come into view. `useOnScreen` is true while any part is in the window, so a loop can pause when it cannot be seen. Without `IntersectionObserver` both are true.                                                                                                                                                                                                                                                                                                                                             |
| `usePageVisible`                   | False while the tab is in the background.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `useScrolled`                      | True once the window has scrolled more than 8 px (or an amount it is given). It reads at most once per animation frame and re-renders only when the answer flips. Both headers use it for their edge and shadow.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| `useLoopClock`                     | A clock for a short looping sequence, driven by animation frames. It adds up the gaps between frame timestamps (never more than 100 ms for one frame) and shows about 30 times a second. `paused` freezes it, `reduced` never starts it and gives the final frame, and after `maxLoops` loops it stops on the final frame. The landing call preview runs on it.                                                                                                                                                                                                                                                                                                                                  |
| `mergeRefs`                        | One ref for an element that needs several, such as a card that is both tilted and watched.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |

`useTilt` is used by the scenario cards, the landing call preview and the tip card in hand, and `useDragScroll` by the carousel and the scenario workspace's product rail. A sliding indicator is a separate hook, `useSlidingIndicator` in `web/src/app/shell/`: it measures the current item and writes `--ind-x`, `--ind-w`, `--ind-by`, `--ind-cy` and `--ind-o` on its container, and the stylesheet moves one element with `transform` only. The header uses it under the current link, and the call preview under the chosen tab. A further file, `use-attached-ref.ts`, keeps listeners with their element when it is replaced; it is internal and not exported.

Each hook has its own test file. They run in jsdom with stand-ins for media queries, observers and animation frames (`interaction/test-utils.ts`), so they show the logic, not how a real mouse or trackpad feels. `e2e/carousel.spec.ts` and `e2e/landing.spec.ts` drive a real mouse drag and a card's tilt in Chromium.

## Shell and routing

`web/src/app/router.tsx` builds a React Router data router with three layouts: **public** (`/`, `/responsible-ai`, `/about`, the not-found page), **app** (`/scenarios`, `/scenarios/:id/brief`, `/sessions/:id/report`) and **call** (`/calls/:id`, which has no navigation, only a skip link and `main`, so the call has the whole screen).

- The public header is the wordmark, **Scenarios**, **Responsible AI**, the theme switch and the main action **Start call**; below 48em the two links fold into a disclosure menu while the switch and the action stay in the bar. On a phone the bar is one row, with the menu button, the theme switch and **Start call** together on the right: the button and the switch are 44 px squares that touch, below 30em the button's word is hidden from the eye and kept for a screen reader, and on the narrowest phones the gaps close up so the bar does not wrap. The app header names the section, shows the provider status (always "Demo mode" when it is, never a guess when the config did not load), offers a way back and has the theme switch (in the bar from 48em, in its menu below that). Below 48em the status is a compact "Demo" or "Live" chip with a chevron, a button that opens that menu and is at least 44 px high. The footer is one line of text, three links and the theme choice (Light, Dark, System): up to 48em every link and every segment of the choice is 44 px high, and above it they are at least 24 px; "Saved on this device" hangs above the choice instead of taking room beside it, so the footer stays one slim row. The call page has neither header nor footer.
- Both headers gain a hairline edge and a soft shadow once the page has scrolled more than 8 px (`useScrolled`), with no blur and no change of height. The public header has one indicator that slides under the current link when the route changes; it is hidden where no link is current (the home page) and its first placement is not animated.
- Every page is a lazy route and a default export. Titles go through `useDocumentTitle`; the page's place in the app header goes through `useAppSection`.
- After a client navigation, focus moves to the section a `#hash` names, or to `main` for a new path. A query-only change and the first load never move focus.
- Each layout has its own error boundary, so a failing page keeps the header and footer around a short message (`ErrorMessage`: not found, did not load, something went wrong). It never shows the error's own text. A failed lazy chunk offers a reload.

| Anything else | A feature's own short prefix: `lp-` for the landing page, `ct-` for the content pages, `scn-` for the scenario workspace and `brf-` for the case brief, `cw-` for the call workspace, `tp-` for the tips strip and `rp-` for the report; `gx-` and `cg-` for the development galleries. |

A feature stylesheet must never be the subject of a rule on an `ff-*` class: it scopes its changes under its own class. Joined selectors (`.ff-button.cw-x`), descendants (`.cw-x .ff-button`) and `:has` scopes are allowed. A test (`class-ownership.test.ts`) scans every stylesheet under `web/src`, works out which class each rule is about (a scoped rule is about the class that scopes it) and fails if two stylesheets are about the same class, so a bare `.ff-button` rule in a feature stylesheet would clash with the design system's own. A second check there holds the classes that live in the design folder to a design prefix (`ff-`, `gx-`, `l-`, `t-`, `u-`), apart from `visually-hidden`, `skip-link`, `measure` and `no-print`. The stricter rule, that a stylesheet names no `ff-*` class at all, holds only for the landing and content folders, where `web/src/features/content/styles.test.ts` enforces it (and checks there that colours are tokens and every font size comes from the type scale); the scenario, call, tips and report stylesheets do scope rules onto design classes such as `.ff-segmented__item`.

## Contrast and accessibility

Contrast is measured from the tokens by a test (`tokens.test.ts`, which also covers the motion tokens), in both themes, so a colour change that fails fails the build. In each theme the test checks 87 text pairs at 4.5:1: body text on every page surface, text on the hover, pressed and selected fills, white on the brand and danger fills, the brand as text and as a link under the pointer, every status and every customer mood on its own tint, the evaluator's accent, every product accent on its tint and on the page, and the report's removed and added words. It checks at 3:1 the edge of a control (`--stroke-accessible`), the selected edge, lines and the error edge, the focus ring, both voices of the waveform, the fills of bars and switch parts, and the chart line; the chart's axis text is held to 4.5:1 and its grid only to being told from the page (above 1.1:1). The lowest text pair is 4.75:1 in the light theme (the purple accent on its tint) and 4.55:1 in the dark theme (white on `--brand-hover`). The test checks the pairs it lists; it does not scan every rule in every stylesheet.

## Changing the system

1. Use an existing token or primitive. If none fits, add it to `web/src/design` with its own stylesheet, a gallery entry and a test, rather than styling it inside a page. A new colour token goes in both themes unless it is an alias of tokens that already are (as `--diff-*` and `--chart-*` are): `tokens.test.ts` fails if the dark block lacks a colour or depth token that the light block declares, or declares one the light block does not. Add the pairs the token takes part in to the contrast test.
2. Keep names additive: do not rename or remove an export, a prop, a class or a token that a page uses. Change values instead.
3. Take every time and distance from the motion tokens and give each new one its reduced-motion value; `motion.test.ts` and `tokens.test.ts` fail otherwise. The spring easing is for the four places in the Motion rules, and `motion.test.ts` holds that list.
4. Run `npm run dev` and open `/gallery.html` to see every state, then check the result at 320 px and 1440 px, with the keyboard only, with reduced motion, with forced colours and in both themes. The app's header has the theme switch; the galleries have none, so follow the device's setting or set `firefly.theme` in local storage to `light` or `dark` and reload.
5. A new dependency needs a reason in the commit message. The browser bundle contains React, React Router and Firefly's own code. `zod` is a server-side dependency and stays out of the browser bundle: the web app imports only types and plain constants from `shared/`.
